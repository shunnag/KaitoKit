## 出自・CLDR 表・判定器の不変性

UniversalDetector / XADMaster / The Unarchiver の実装ソースは参照していない。udet は支給された黒箱実行ファイルだけを使用。
文字コードの対応は Python 標準 codec と CF、VISCII は支給 RFC 1456、言語集合は CLDR の main / auxiliary だけを使う。
記事名を辞書・頻度表・規則へ転用していない。MIT と既存 API を維持する。

CLDR は既存19集合（測定18言語＋en）と追加21集合、合計40集合を生成した。
Swift ファイルは **160,303 → 174,274 bytes**（+13,971 bytes、+8.72%）。閉区間の圧縮方式は不変。
既存 `table` の配列内容はバイト一致し、追加分は `additionalTable`、集合検査用は `allTable` として保存する。
現行採点器は `table` だけを参照し、C-B で候補への接続と UInt32 言語マスクの拡張を行う。
全40集合を現在の採点器へ直結すると、ソートした言語番号が32を超えて既存言語のマスクが失われるためである。

`nb.xml` は identity だけで、CLDR の
[parentLocale 宣言](https://github.com/unicode-org/cldr/blob/main/common/supplemental/supplementalData.xml)に従って
[no.xml の主・補助集合](https://github.com/unicode-org/cldr/blob/main/common/main/no.xml)を継承する。
初期の支給ディレクトリには no.xml がなかったため、公式 XML の主・補助要素だけを `.build/cldr-c/no.xml` に保存して生成した。
他の XML と LICENSE は支給入力への symlink。生成器は no.xml を含む未到着・空ファイルを30秒ごと、最大10分待つ。
通常の再生成には完全な公式 no.xml を入力ディレクトリに置けばよく、ネットワーク処理を生成器には入れていない。

`EncodingDetector.swift` / `NameEncodingCandidates.swift` / `NameEncodingScorer.swift` / `EncodingPolicy.swift` /
`Sources/kaito/DetectEncoding.swift` とルート NOTICE は HEAD とバイト一致。
初回の追加表生成直後の release は、生成前に固定した PR #21 と SHA-256 が一致していた（初回記録は `.build/task-c-stale/`）。
現在の `.build/release/kaito` はその固定版とハッシュが異なるため、今回の測定物としては参照しない。
訂正3では開始時から固定した `.build/task-c-before/kaito` を all / tune / eval に使用し、各reportの `kaito_sha256` と照合した。
SHA表と下記測定コマンドも、実際に使用したこの固定実行ファイルを指す。

## VISCII の出典と検証

[支給 RFC 1456](../../inbox/specs/rfc1456-viscii.txt) の §3 Table 1（VISCII v1.1）を、
§4 Table 2 の VIQR 記号から Unicode に転記した自前表。出典 URL は
[RFC Editor の RFC 1456](https://www.rfc-editor.org/rfc/rfc1456.txt)。生成器内の256表を符号化・復号で共有する。
0x80–FF の128文字に、C0 の6文字（02=Ẳ、05=Ẵ、06=Ẫ、14=Ỷ、19=Ỹ、1E=Ỵ）を加えた134文字。
ASCII 図形文字と残りの制御位置は保持し、置換された制御文字を同じbyteへ二重に符号化しない。

`test-name-corpus.py` は RFC の16行×16列の座標と VIQR から期待表を独立に復元し、
生成器の全256位置、134文字の一意性、各文字の符号化→復号、全256 bytes の復号→符号化を確認した。
C0 の6制御 scalar 自体は符号化できず、未対応文字も strict encode が失敗することを検査した。
測定器はこの codec の登録と IANA / MIME の対応だけを追加し、CF による正解復号・除外・採点を変更していない。

現行 CF は `viscii`（CF 0x0A07）と NSString encoding の往復を認識するが、
拡張128byteは復号 FAIL、C0 の6位置は制御文字に復号される。Python の RFC 表と異なる位置は正確に134。
このコーパスの VISCII は全行が codec-mismatch で分母0。C0再割当位置を使う実記事由来行は0件だったが、6位置の往復は上記単体検証で網羅した。
ASCIIだけのbytesや厳密UTF-8 bytesの除外も従来どおりなので、C0文字だけの名前を精度評価するコーパスではない。
C-B では VISCII の自前復号を接続した後に、正解復号の分母を再確認する必要がある。
NOTICE は C-A の指示どおり不変で、RFC 出典は生成器コメントと本記録に残す。

## 再現コマンド

**生成器を変更したら、既存コーパス・測定結果・記録を有効な最終結果として使わず、必ず全 split を再生成・再測定し、全表と SHA を作り直す。**
最終保存後に生成器と入力のハッシュ・mtimeを固定し、別プロセスで2回生成する。各コマンドの終了コードとファイル一致を検査し、失敗時は先へ進まない。

no.xml を含む CLDR の親入力を揃えた通常環境では `--cldr-dir inbox/cldr` を使用する。
