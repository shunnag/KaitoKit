# xar reader 検証記録(2026-09-09)

対象コミット: `deed11d`
実装: `Sources/KaitoKit/Formats/Xar/`(XarHeader / XarXMLParser / XarTOC / XarReader)

## 1. 方法

XADMaster をブラックボックスの展開オラクルとしてのみ使用する(design.md §10)。
比較は `$W/bin/xadsha`(XADMaster)と `$W/bin/rectest`(KaitoKit)の
`index / size / sha256 / name` 出力で行う。並びは両者一致するため(§4.1)、
**順序込みで `(size, sha256)` の列をそのまま**突き合わせる。

fixture の作成には macOS の `/usr/bin/xar` 1.8dev と `pkgbuild` を
ブラックボックスの writer としてのみ使い、lzma / xz / subdoc など
`/usr/bin/xar` が書けない形は公開仕様から Python で自作した。

## 2. 形式の実測

header は 28 byte・big-endian:

| offset | size | 内容 |
|---|---|---|
| 0 | 4 | magic `xar!` |
| 4 | 2 | header size(実測 28。**この値で seek する**) |
| 6 | 2 | version(1) |
| 8 | 8 | 圧縮 TOC 長 |
| 16 | 8 | 非圧縮 TOC 長 |
| 24 | 4 | TOC checksum algorithm |

`--dump-header` の実測で algorithm は sha1=1 / sha256=3 / sha512=4。
heap は圧縮 TOC の直後、すなわち `headerSize + compressedTOCLength` から始まる。
TOC は **zlib 生 stream(RFC 1950、`78 da` で始まる)**。

### TOC checksum の被覆範囲(実測で確定)

`<toc><checksum style="..."><size>N</size><offset>0</offset></checksum>` は
**heap 内**の digest の位置を指す。digest は**圧縮後の TOC bytes**に対するもの。

| fixture | alg | style | 圧縮 TOC 一致 | 非圧縮 TOC 一致 |
|---|---|---|---|---|
| pkg.xar | 1 | sha1 | **true** | false |
| toc-sha256.xar | 3 | sha256 | **true** | false |
| toc-sha512.xar | 4 | sha512 | **true** | false |
| real.pkg (pkgbuild) | 1 | sha1 | **true** | false |
| comp-bzip2.xar | 1 | sha1 | **true** | false |

### `<data>` の offset / size / length(実測で確定)

`<size>` = 展開後サイズ、`<length>` = heap 上のバイト数、`<offset>` = heap 先頭からの相対位置。
pkg.xar の b.bin は実体 4096 byte に対し `<size>4096</size> <offset>20</offset>
<length>309</length>` で、次の member の offset が 329 = 20+309 と連鎖する。

`<data>` の子要素の順序は固定ではない。pkgbuild の出力は
`<size> <offset> <encoding/> <length>` の順だった。位置ではなく名前で拾う。

## 3. encoding style と codec(オラクルで確定)

| style | heap 上の中身 | 根拠 |
|---|---|---|
| `application/octet-stream` | 無圧縮 | pkgbuild の Payload |
| `application/x-gzip` | **zlib 生 stream(RFC 1950)** | heap 先頭が `78 da`。gzip container ではない |
| `application/x-bzip2` | bzip2 | `--compression=bzip2` |
| `application/x-lzma` | **LZMA_Alone**(13 byte header) | 自作 fixture を XADMaster が展開 |
| `application/x-xz` | xz stream | 自作 fixture を XADMaster が展開 |

判別実験: `application/x-lzma` と宣言して xz payload を入れた書庫は
XADMaster が 0 byte を返した。つまり XADMaster は sniff しない。
KaitoKit は magic を見て xz なら xz として扱う(XADMaster を超える許容)。

## 4. 並びと、XADMaster との意図的な差異

### 4.1 並びは一致する(当初の誤りの訂正)

調査の途中で「XADMaster は `<toc>` 直下の兄弟を逆順に走査する」と一度結論したが、
**これは誤りだった**。根拠にしていたのは `xar --dump-toc` の出力である。

実測: TOC を自前で inflate して生 bytes の `<name>` 出現順を見ると

| fixture | 保存されている TOC の順 | `xar --dump-toc` の表示順 |
|---|---|---|
| corpus/xar.xar | c.rnd, a.txt, sub, nested.md, 日本語, b.bin | b.bin, sub, nested.md, 日本語, a.txt, c.rnd |

`xar --dump-toc` は保存された XML をそのまま出さず、内部表現から兄弟を逆順に
再生成して表示する。XADMaster も KaitoKit も**保存順(親が子より先の pre-order)**
で entry を出しており、両者の並びは一致する。
並びの根拠には必ず inflate した生 bytes を使うこと。

この訂正により、順序に依存する総合 digest をそのまま比較できる(§5)。

### 4.2 `<name enctype="base64">` の復号

`/usr/bin/xar` は UTF-8 の日本語ファイル名を base64 で格納する。
XADMaster はこれを復号せず `5pel5pys6KqeLnR4dA==` のまま表示する。
KaitoKit は復号して `日本語.txt` を返す。
第 2 のオラクルとして `/usr/bin/xar -x` で展開すると、ディスク上の実ファイル名は
`日本語.txt` であり、KaitoKit 側が正しいことを裏づける。
内容 digest は一致するので、この差は名前だけに現れる。

### 4.3 `<subdoc>` 内の `<file>`(セキュリティ上の差異)

`<toc>` には `xar -s` が書く任意の XML(`<subdoc>`)が入る。
実測: **XADMaster は `<subdoc>` の中に置いた `<file>` を実在の entry として公開する**。
細工した subdoc で偽 member を注入し、heap の任意範囲を読ませられる。

自作 fixture `xar-subdoc.xar` は `<subdoc>` に `<file id="99">ghost.txt` を仕込む。
XADMaster は 3 entry(ghost.txt を含む)、KaitoKit は 2 entry で ghost.txt を出さない。

### 4.4 TOC checksum の検証

heap 先頭に置かれた TOC digest だけを 1 byte 壊した書庫を作った。
XADMaster はそのまま 10 entry を返す。KaitoKit は
`Malformed archive: xar toc checksum mismatch` で開封を拒否する。

### 第 2 のオラクル(`/usr/bin/xar -x`)

`xar-plain.xar` を `/usr/bin/xar -x` で展開し、ディスク上の実体と突き合わせた。

* 内容 SHA-256 は全ファイルで KaitoKit / XADMaster と一致。
* 実ファイル名は `日本語.txt`(§4.2 の裏づけ)。
* `a.txt` と `hard.txt` は同一 inode。`link.txt -> a.txt` の symlink。

## 6. 敵対的入力

すべて具体的な診断で停止し、最も遅いもので 3.4ms。

| 入力 | KaitoKit の応答 | 時間 |
|---|---|---|
| 圧縮 TOC の 1 byte 反転 | malformed: invalid zlib stream(Adler-32 で検出) | 0.2ms |
| heap 先頭の TOC digest だけ破壊 | malformed: xar toc checksum mismatch | 0.6ms |
| pkg の stored member を 1 byte 反転 | malformed: xar checksum mismatch(stream 完了時) | 3.4ms |
| 圧縮 TOC 長がファイル超過 | truncated | 0.1ms |
| 非圧縮 TOC 長 = 1 TiB | limitExceeded(16 MiB 上限、確保前に停止) | 0.1ms |
| version = 2 | unsupportedFormat | 0.2ms |
| header size = 27 | unsupportedFormat(probe が成立しない) | 0.2ms |
| `<!DOCTYPE` | malformed: xar toc doctype | 0.2ms |
| 実体参照 `&lol9;` | malformed: xar toc entity | 0.2ms |
| member の offset+length が heap 超過 | truncated | 0.5ms |
| XML 入れ子 5,000 段 | limitExceeded: xar toc depth | 0.9ms |
| stored なのに length != size | malformed: xar stored size | 0.5ms |
| 未知の encoding style | unsupportedMethod(entry 単位。一覧は成功) | 1.4ms |
| 大文字 `style="SHA1"` + 不正 digest | malformed: xar checksum mismatch | 0.9ms |

DTD と実体参照を入口で拒否しているため、billion laughs 系は展開されない。

## 7. 退行確認

* コーパス 103 書庫: 88 が開き 15 が開かない。開かない 15 はすべて未対応形式
  (brotli / lz4 / zstd / DMG / WIM / uuencode)か想定内の状態(パスワード必要、
  分割書庫の継続部)で、xar 由来の退行はない。
  hardlink 修正・codec 追加の前後で全 103 書庫の結果を突き合わせたところ、
  差分は error 経路の所要時間 (0.1ms→0.4ms 程度) だけで、開いた 88 書庫の
  entry 数と総合 digest はすべて同一だった。
* `DeflateDecompressor` は既定 (`zlibWrapped: false`) の挙動を変えていないため、
  ZIP と 7z の deflate 経路は上の digest 一致がそのまま裏づけになる。
* `swift test`: 738 test(37 skip)+ compat 20 test、失敗 0。うち xar は
  `XarReaderTests` 10 件、`CLISmokeTests` の展開検査、`KaitoArchiveXarTests` 1 件。

## 8. 展開(hardlink の前方参照)

読み取りだけでは出ず、実際にディスクへ展開して初めて出る不具合を 1 件見つけて直した。

xar は実体を持つ member を参照より **後ろ** に置く。`xar-plain.xar` では
`a.txt`(index 1)が `hard.txt`(index 7)を指す。一方 `Extractor` と compat 層は
「target は自分より前の index」を前提にしていた。これは tar / RAR5 の reader が
直前の正規化名からしか index を発行しないために成り立っていた前提で、xar では崩れる。

修正前(ベースライン):

```
error: failed entry 1 (a.txt): Malformed archive: hard-link target is not a prior archive member
error: failed entry 2 (l2.txt): Malformed archive: hard-link target does not match its archive member
```

直した内容は 3 つ。

1. `Extractor.archivedHardLinkTarget` と `KaitoArchive.extractionChain` の
   `targetIndex < index` を `targetIndex != index` に緩める。安全性は index の前後関係では
   なく、`trustedTargets` に **この reader が同じ root へ実体を展開した inode** があること
   と、`linkPath` が target entry の名前と一致することで担保される。
2. 前方参照は実体の展開後まで待つ(`Sources/kaito/main.swift` の展開ループ)。
   後方参照の処理順は変えていない。`ArchiveReader.extract` は 1 entry 単位の API なので、
   遅延は loop を持つ側の責務であることを doc comment に明記した。
3. `XarReader` が `linkPath` と `hardLinkTargetIndex` を同じ entry(最終的に実体を持つ
   file)に揃える。chain のとき前者が直近 id、後者が終端を指していて食い違っていた。

修正後(`xar/extract-check.sh`):

```
xar-plain.xar/a.txt      OK   1ddc234bae1b3930239b3d8625224117828d8a576bb8951087cbe6097387fb1e
xar-plain.xar/hard.txt   OK   同上
  inode: 84222589 が両方  ← 実体の hard link が張られている
xar-links.xar/orig.txt   OK   86d7bb82c5856157d89466dc8fc8d52b8e14742702359f500dd09f0f912bb77c
xar-links.xar/l1.txt     OK   同上
xar-links.xar/l2.txt     OK   同上(orig ← l1 ← l2 の chain)
```

`dangling.txt`(`link="404"` が存在しない id を指す)は entry 単位で失敗する。
XADMaster は空ファイルを返すが、壊れた参照は具体的な診断で拒否する方を採る。

## 9. 再実行手順

```
# 測定用ハーネスは release build の dylib を @rpath で拾うため、
# ソース変更後は必ず release を建て直してから測る。
cd <repo> && swift build -c release
<corpus>/xar/verify.sh          # XADMaster との厳密比較(順序込み)
<corpus>/xar/extract-check.sh   # 実際にディスクへ展開して hardlink を検査
cd <repo> && swift test
```

fixture の作り方と payload の SHA-256 は `Tests/Fixtures/NOTICE` に記録した。
自作 writer(`<corpus>/xar/mkxar.py`)は公開仕様から組んだもので、
生成物はすべて XADMaster を展開オラクルとして検証している。
