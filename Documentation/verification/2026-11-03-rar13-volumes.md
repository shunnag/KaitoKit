# RAR 1.3 / 1.4 old multi-volume の検証

対象: cooViewer-c1vj.13。`RE~^` の old `.rar` / `.r00` 分割を、同じ directory の
決定的な兄弟名だけで解決し、stored・非 solid 圧縮を展開する。

## 入力資料と実装

- [RAR 1.3 / 1.4 format notes §9](https://github.com/bitplane/rar-research/blob/master/doc/RAR13_FORMAT_SPECIFICATION.md)
  の `MHD_VOLUME`・`LHD_SPLIT_BEFORE`・`LHD_SPLIT_AFTER` を使う。
- `RAR13VolumeLocator` は directory anchor と先頭 volume の identity を検証し、
  各続巻の `RE~^` も確認する。任意の兄弟 file は開かない。
- 各 volume は独自の main / file header を持つ。継続 file は新しい entry にせず、
  name・method・version・comment を照合して `SourceSegment` を連結する。
- 最終 part の 16-bit rolling checksum を使う。Data からの継続巻解決と solid 分割は拒否する。
- 自作 2 巻は `Scripts/fixtures/make-rar13-volumes.py` が生成し、UNRAR 7.23 の `t` と `x`
  でも stored・圧縮が元入力と一致することを確認した。

## 確認した結果

- `RAR13ReaderTests`: **20 tests / 0 failures**。
  - 自作 stored・圧縮の 2 巻を URL から展開し、元入力と全 byte 一致。
  - Data の継続巻解決は `unsupportedMethod`、欠巻は `truncated`、name の異なる続巻は `malformed`。
    `maxVolumeCount = 0 / 1` では 1 / 2 巻目を開かず `limitExceeded` になることを確認。
  - 実 RAR 1.402 の `CMULTIV.RAR`（8 巻）と `MULTIVOL.RAR`（4 巻）が UNRAR 出力と一致。
  - `volumeSegmentCount` と最終巻の checksum を確認。
  - 既存の通常・solid・暗号・comment・SFX・checksum 検査にも退行なし。
- `RAR15DecoderTests`: **7 tests / 0 failures**。
- ASan 付き CLI（`swift build --scratch-path .build/rar13volumes-asan --sanitize=address --product kaito -j 4`）
  と Release CLI（`swift build -c release --scratch-path .build/rar13volumes-release --product kaito -j 4`）
  で、実 RAR 1.402 の 4 巻・8 巻と自作 2 巻が UNRAR 出力と一致した。
  実 8 巻の payload・checksum を変えた 128 件も **sanitizer finding / crash / hang /
  誤った正常出力 0**（受理 1、通常の展開 error 127）。
- 全 suite: KaitoKit **2,086 tests / 58 skipped / 0 failures**、Compat **34 tests / 0 failures**。
  test 本体は **1,426.955 秒**。巻数上限の最終修正は対象 test でも再確認済み。

## 対象外

Data からの継続巻解決と solid 分割は対象外。custom RAR VM と CAB Quantum は別課題とする。
