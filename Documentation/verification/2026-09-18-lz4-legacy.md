# LZ4 legacy frame の読み取り追補（2026-09-18）

環境: macOS 27.2 / Apple Silicon / Xcode 27.0。macOS 26 と Intel の実行結果は含まない。

## 実装と範囲

- LZ4 legacy magic `0x184C2102`、最大8 MiBの独立block、EOFまたは次frameのmagicによる終端を扱う。
  公開仕様に記載されたLinuxの4 zero byte終端にも対応する。
- 現行frame・legacy・全16種のskippable frameを混在して読み取る。
  先頭がskippableの場合もlegacyを識別し、単体 `.lz4` と `.tar.lz4` の既存入口に接続する。
- block間の辞書参照を許可せず、圧縮入力・展開結果を各1 blockまで保持する。
  圧縮サイズにはblock grammarから導いた上限を先に適用し、metadata走査はpayloadを読み込まない。
  一項目・全項目・メモリread・frame/block件数の上限を、連結後半にも適用する。
- **legacyにはchecksumと宣言サイズがない**。block内部での切り詰めは拒否するが、
  末尾のblockを丸ごと失った入力は短い正常streamと区別できない。
- KaitoFinderで単体・圧縮tarのプレビュー内容を照合し、圧縮tarの読み取り専用判定と変換名を確認した。
  外部辞書と新規LZ4出力は引き続き未対応。

実装入力は [LZ4 Frame Format v1.6.4のLegacy frame節](https://github.com/lz4/lz4/blob/dev/doc/lz4_Frame_format.md#legacy-frame)
と既存の [LZ4 Block Format](https://github.com/lz4/lz4/blob/dev/doc/lz4_Block_format.md)。
第三者codec実装ソースは用いていない。製品は外部CLIを起動しない。

## 独立データとCLIの差

プロジェクト所有の入力を **LZ4 1.10.0 CLI** の `-l` で圧縮・展開した6 fixtureを追加した。
空、1,033 byte、8 MiBちょうど、8 MiB+53 byte、圧縮しにくい入力、USTARを含む。
既存の現行frame 10 fixtureは、manifestとbytesが変更されていないことを照合した。

さらにテスト実行時に8 MiB+17 byteのxorshift32入力を作り、CLIで圧縮・展開する。
圧縮後のblockが8 MiBを超えても受理し、元の全byteと一致することを確認した。
大きな非圧縮データを固定fixtureとして追加していない。

| 入力 | LZ4 1.10.0 CLI | KaitoKit |
|---|---|---|
| legacy → legacy / legacy → 現行 / legacy → skippable → 現行 | 全内容一致 | 全内容一致 |
| 現行 → legacy / 現行 → skippable → legacy | 後半で `ERROR_frameType_unknown` | 各frameを順に展開 |
| Linux zero終端 | exit 64 | 公開仕様の拡張として受理 |
| 短いlegacy blockを同frame内で連結 | 全内容一致 | 互換性のため受理 |

混在の両方向とzero終端はテストしているが、CLIが拒否する条件をCLI互換成功とは数えない。

## 検証

- LZ4専用 **19件、失敗0、skip0**（7.803秒）。
  全16 fixtureのSHA、8 MiB境界、連結、全skippable magic、独立履歴、切り詰め、
  不正サイズ・sticky error・上限を確認した。
  圧縮tarはメモリ／ディスクstaging、128 byte単位の `.001` 分割、unlink後のreopen、
  全memberの内容一致を現行・legacyの両方で確認した。
- KaitoKit全件 **1,195件、失敗0、skip43**（379.874秒）。
  今回は手元のCAB・暗号化StuffItの外部corpusを環境変数で有効にして実行した。
  Compat **24件、失敗0、skip0**（1.537秒）。
- GyoshukuKit全件 **202件、失敗0、skip0**（506.238秒）。
  `GYOSHUKU_LARGE_TAR_TESTS=1` とし、4 GiB超の圧縮tarとZIP64の実ファイル検証も含めた。
- KaitoFinder関連 **65件、失敗0、skip0**（16.779秒）。
  プレビュー用の実ファイルのSHAと読み取り専用判定を含む。実画面の成功件数ではない。
- ASan/UBSan: 8 seed・圧縮payload範囲必須で **320変異、crash0・hang0・診断0**。
  同じsanitizerビルドで正常16 fixtureも全SHA一致・診断0。
- Python構文検査と3リポジトリの `git diff --check` が成功した。
