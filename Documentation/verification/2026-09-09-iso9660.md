# ISO 9660 reader 実装・検証記録（2026-09-09）

実装は Swift 6、Foundation と既存 KaitoKit 基盤のみ。Package.swift / 依存関係は変更していない。
Git commit、bd、xcodebuild コマンドは直接実行していない。変更は作業ツリーに保持する。

## 実装入力と判断

利用者指定の PLAN.md / ORACLE.md を全文読み、公開仕様の byte 表を実装入力にした。
資料の出自は ECMA-119、Microsoft Joliet、IEEE P1281（SUSP 1.10）、IEEE P1282（Rock Ridge）、
Apple Technote FL 36。ORACLE.md は black-box 実測値・木の選択判断にのみ使用した。
禁止対象の第三者 reader/writer の source は読まず、引用・参照していない。web 検索は行っていない。

- 木の順序は **Rock Ridge（NM あり）> Joliet > PVD**。日本語コメントを reader に記録した。
  RR + Joliet の 3 symlink が消える XADMaster の挙動とは意図的に異なる。
- NM は複数 SUSP/CE にまたがって連結し、既存の archive-wide UTF-8 / CP932 / EUC-JP 判定を使う。
  Joliet の 3 escape sequence、UCS-2BE、奇数長・不正 surrogate の縮退に対応する。
- SP / CE / NM / PX / SL / TF / RE / CL / PL を解析する。CL は移転先の '.' から実体を読む。
  RE の実体を非表示にし、Joliet では relocation を適用しない。directory は 0 byte で公開する。
- logical block size 512/1024/2048、EA block、version 除去、multi-extent の byte 連結に対応する。
  単一 extent は既存 CopyDecompressor を使う。
- ReadLimits を実際に適用し、PVD/Joliet の両走査を共通の metadata 予算に加算する。
  directory の深さは `ReadLimits.maxPathComponentCount`(既定 1,024)を上限とし、
  超過は `limitExceeded("iso directory depth")` を投げる。CE 8 連鎖、file 64 section、
  directory 65,536 個に制限する。
  ancestor extent の循環を打ち切り、CE 循環、extent 範囲外、record の sector 跨ぎを拒否する。
  record 長 0 は次の sector へ進む padding とする。
- PLAN の検出挿入位置からは変更し、既存 ZIP EOCD 復旧 / SFX の後に CD001 を検査する。
  ユーザーの「従来検出できた書庫を ISO と誤判定しない」を優先した。
  CD001 を payload に含む damaged native ZIP / PE SFX の回帰テストを追加した。
- record の sector 跨ぎは、PLAN の寛容な skip より厳しい malformed とした（ユーザーの拒否要件）。

## 独立検証(orchestrator による再実測)

Codex の報告とは別に、同じ画像を自分で測り直した。

### XADMaster との総合 SHA-256 の一致

総合 digest は「各 entry の内容の SHA-256 を 16 進小文字にし、その UTF-8 byte を順に
連結して再度 SHA-256」。**順序も含めて**一致することを要求する。

| 画像 | entry | 総合 SHA-256 | 判定 |
|---|---:|---|---|
| `plain.iso` | 12 | `e7ebbb1323…` | **XADMaster と完全一致** |
| `joliet.iso` | 12 | `cdaada2d36…` | **完全一致** |
| `hybrid.iso` | 12 | `e7ebbb1323…` | **完全一致** |
| `rr/plainonly.iso` | 16 | `f12af6ac09…` | **完全一致** |
| `rr/rr.iso` | 16 | `f12af6ac09…` | **完全一致** |
| `rr/jol-norr.iso` | 13 | `a102eaf00c…` | **完全一致** |
| `rr/rrjoliet.iso` | 16 | — | XADMaster は 13。差は symlink 3 件のみ(上位集合) |
| `rr/jolietonly.iso` | 16 | — | 同上 |
| `udf.iso` | — | — | 両者とも非対応 |

当初 KaitoKit は**幅優先**で木を辿っており、件数は一致するのに総合 digest が
すべて食い違っていた。XADMaster は**深さ優先の先行順**。件数だけを見る検査では
見逃す差だったので、深さ優先に揃えた。

### Joliet 復号経路の独立確認

digest は内容だけを見るため、名前の誤りを検出できない。そこで名前・サイズ・SHA-256 の
三つ組を名前順に並べて比較した。

- `joliet.iso`(hdiutil 製。RR を名乗るが **NM が無い**ので Joliet 経路に落ちる)は
  XADMaster と三つ組が完全一致。`日本語ファイル.txt` と
  `a-rather-long-file-name-for-joliet-testing.txt` が正しく復号されている。
- さらに `xorriso -as mkisofs -J --norock` で **SUSP を一切含まない** Joliet 専用画像
  `rr/jol-norr.iso` を作り、Joliet decoder だけが働く状態でも完全一致することを確認した。

### 敵対的な画像

`plain.iso` を改変して 3 種を作り、20 秒の上限付きで実行した。

| 改変 | KaitoKit | XADMaster |
|---|---|---|
| directory record の extent を image 末尾より先へ | `truncated` で拒否(0.01s)| 開けない |
| 子 record を root extent へ向けて循環させる | **0.01s で完了**、循環を検出して枝刈り(12 entry)| **99% CPU で 30 秒以上終わらない** |
| sector 途中で record 長を 0 にしゴミを続ける | 0 件で成功(0.01s)| 0 件で成功 |

循環画像で XADMaster は無限ループする。KaitoKit は `ancestors` に extent を積んで
明示的に検出しており、深さ上限で偶然止まっているのではない。

record 長 0 は ECMA-119 では「次の logical sector へ進む padding」なので、
0 件で成功するのは両者とも仕様どおりの挙動である。

### 深さ上限の是正

内部固定の 64 階層で打ち切り、`specific["truncatedTree"]` を付けて**黙って部分木を落として
成功を返して**いた。`ReadLimits.maxPathComponentCount` の既定は 1,024 なので、利用者が
設定した上限は決して届かない。tar と ZIP は同種の超過を `limitExceeded` で投げる
(`TarReader.swift:409`、`ZipReader.swift:1648`)ため、流儀とも食い違っていた。

`maxPathComponentCount` を深さの上限として使い、超過は
`limitExceeded("iso directory depth")` を投げるようにした。循環の枝刈りは
役割が異なる(壊れた構造から読める分を返す)ので、そのまま残している。

### 既存書庫への影響

コーパス 95 書庫で、ISO 検出の追加により判定が変わった書庫は無い。開けない 15 件は
すべて既知の未対応形式(ar / cpio / xar / wim / uue / brotli / lz4 / zstd / dmg /
7z 分割)と、生成に失敗した 0 byte の `plain.gz` である。

`swift build -c release` 成功、`swift test` 終了コード **0**、693 test・0 failure(33 skip)。
