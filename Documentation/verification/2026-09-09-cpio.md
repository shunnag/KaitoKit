## 実装入力と仕様判断

利用者指定の PLAN.md（52,941 bytes）と ORACLE.md を全文読んだ。
形式の入力は POSIX / IEEE Std 1003.1、cpio(5)、GNU cpio manual、Heirloom cpio(1)、
Linux initramfs buffer format、HP-UX cpio(4) の公開仕様・prose から作られた byte 表。
ORACLE.md は black-box 受け入れ値の照合に使用した。禁止対象の source は開かず、
引用・参照していない。CpioReader.swift の先頭と design.md §10 にクリーンルーム宣言を記録した。

- bin（両 byte order）/ odc / newc / crc / hpbin / hpodc に対応。
  HP 変種は同じ envelope として解釈し、in-band の HP 判別や device number の復元は行わない。
- bin の mtime / filesize は上位16 bit wordを先に読み、各 word 内だけ byte order を適用する。
  負の binary filesize を拒否する。odc は無 padding、bin は2 byte、newc/crc は4 byte境界。
- 名前は宣言された namesize 内で終端を検査し、余分な末尾NULは許容する。
  途中の NUL の後に非NUL byteがある名前、空名、未終端名は拒否する。
- hard link は利用者指示を優先し、PLAN §4.6 の実体補完を採用しない。
  宣言0 byteの entry は0 byte、実体を持つ entry は自分の内容だけを返す。
  symlink はdata領域のtargetを内容として返し、formatSpecific["linkPath"] にも記録する。
- crc の通常 file の完全な非空dataを32 bit単純加算で照合する。
  利用者指示を優先し、不一致は read 完了時の malformed。crc32 は nil。
  PLANどおり、paxのcheck=0 symlink、0 byte entry、救済で不完全なentryは照合しない。
- TRAILER!!! は公開せず、NUL padding の後に認識できる magic があれば次の書庫として続ける。
  archiveIndex で区別し、trailer後の未知のごみは無視する。clean EOFも許容する。
  NUL run は1 MiBまで、ちょうど上限なら次の非NULを受理し、それを超えたら走査を終了する。
- entry size/count、name/link allocation、path component count、retained metadata を制限する。
  aggregate output / in-memory read は既存 ArchiveReader / EntryStream の ReadLimits を使う。
  切り詰めはstrictでは拒否。救済時は既読entryを残し、最終dataを残量に制限する。

## 検出回帰

ASCII cpio は compress magic の後・native ZIP EOCD復旧の前で、先頭record全体を検証する。
binary は既存の検出と拡張子hintの後に置き、最大4 record の連鎖を検証する。
大きなdataは読み込まず、計算した次のheader offsetを検証する。

既存コーパス `scratchpad/gap/{corpus,corpus2,corpus3}` の95書庫を変更前・変更後のCLIで比較した。

| 比較群 | 件数 | 実測 |
|---|---:|---|
| 以前からdetect成功 | 81 | 81/81で同じ形式。cpioへの誤判定0 |
| 以前から未対応、cpio以外 | 12 | 12/12で同じunsupported |
| 以前から未対応、実際のcpio | 2 | cpio-newc.cpio / cpio-odc.cpio がunsupportedからcpioへ |
| 別枠の暗号化書庫 | 6 | 6/6不変 |

したがって「95件すべて不変」は文字通りには成立しない。新規対応したcpio 2件だけが変化し、
残り93件は不変。以前検出できた書庫の結果が変わった例はない。
ログ: `/tmp/kk-cpio-detect-{before,release}.json`、手順: `/tmp/kk-cpio-detect.py`。

PLANの `C7 71` LZMA例は、既存detectorが受け入れる辞書サイズ（2^n / 3×2^n、4096以上）に
合致しない。従来どおりunsupportedになることと、通常のLZMA headerの判定が維持されることを
テストした。既存LZMA判定は変更していない。

fallback が unsupportedFormat 限定でなく、KaitoKit open の全失敗を対象にすることも確認した。

## 独立検証(orchestrator による再実測)

### 健全な書庫 — XADMaster との総合 SHA-256

`find . | sort | cpio -o --format=<fmt>` で 10 個の fixture を作った。素材は 12 entry
(`.`、`a.txt` 6 byte、`hardlink.txt`(a.txt への hard link)、`b.txt`、`empty.txt`、
`symlink.txt`、`data.bin` 50,000 byte、`日本語.txt`、`sub/`、`sub/deep/`、
`sub/one.txt`、`sub/deep/two.txt`)。crc / hpodc / hpbin は BSD cpio では作れないため
GNU cpio 2.15(`brew install cpio`)を使った。

| fixture | 生成 | 総合 SHA-256 | 判定 |
|---|---|---|---|
| `bin` / `odc` / `gnu-bin` / `gnu-odc` / `gnu-hpodc` / `gnu-hpbin` | BSD・GNU | `5b136084392db8a1…` | **一致** |
| `newc` / `gnu-newc` / `gnu-crc` | BSD・GNU | `b380629a345afd99…` | **一致** |
| `tar-newc` | `bsdtar --format=newc` | `2f164c10f679679b…` | **一致** |

**10/10 で順序込みの完全一致。**

digest が 2 系統に分かれるのは形式の仕様差である。bin / odc 系は hard link 群の各リンクが
それぞれ実体を持つ(`a.txt` も `hardlink.txt` も 6 byte)のに対し、SVR4 系(newc / crc)は
実体を最後のリンクにだけ格納する(`a.txt` が **0 byte**、`hardlink.txt` が 6 byte)。

この点は文献が食い違っていた。libarchive の `cpio(5)` は「最初のリンク」と書き、
Heirloom `cpio(1)` は SVR4 原典を引いて「最後のリンク」と書く。**実測は最後**だった。
いずれにせよ reader は宣言された filesize をそのまま返せば正しく、補正してはならない。

`tar-newc` が他の newc と digest が違うのは **entry の順序だけ**で、名前・サイズ・内容は
同一である。

### PDP / middle endian の確認

bin 変種の 32bit フィールド(`c_mtime` / `c_filesize`)は上位 16bit word が先に置かれ、
各 word がさらに検出した byte order で swap される。V = (word0 << 16) | word1。
`0x12345678` は little-endian 書庫で `34 12 78 56` になり、素直に u32 として読むと
`0x56781234` になる。これが最大の誤読ポイントなので、`modificationDate` を直接読み出す
probe を書いて確認した。

| fixture | `a.txt` の mtime |
|---|---|
| 原本 | 2026-09-09 14:55:44 |
| `bin` / `gnu-bin` / `gnu-hpbin` | **2026-09-09 14:55:44** |
| `odc` / `gnu-hpodc` / `newc` / `gnu-crc` | 2026-09-09 14:55:44 |

誤読していれば bin 系だけ壊れた日付になる。7 変種すべてが原本と一致した。

### 切り詰め書庫の救済

XADMaster は切り詰めた cpio から読める分を返す。KaitoKit も
`recoverDamagedArchives` で同じことができる。

| fixture | strict | 救済 ON | XADMaster |
|---|---|---|---|
| `newc-t60` | `truncated` | 3 entry `d00f16cf98…` | **一致** |
| `newc-t90` | `truncated` | 3 entry `49f319ced3…` | **一致** |
| `odc-t60` | `truncated` | 4 entry `296b310d9c…` | **一致** |
| `bin-t60` | `unsupportedFormat` | 4 entry `dd08768ab0…` | **一致** |
| `bin-t90` | `unsupportedFormat` | 4 entry `084cb31249…` | **一致** |

binary 変種は当初、救済モードでも `unsupportedFormat` で落ちていた。magic が 2 byte しか
無いため誤検出防止として record chain 全体の検証を要求する設計にしてあり、切り詰められた
書庫は chain が完結しないためである。救済フラグが有効なときに限り、**最低 2 個の record が
完全に検証できたうえで EOF に達した** chain を受理するようにした
(`CpioHeader.probeBinary` の `recoverDamagedArchives && index >= 2`)。
フラグを第一 conjunct に置いてあるので、既定では到達し得ない。

`bin-t60` では `data.bin` が 50,000 中 30,258 byte まで部分救済され、XADMaster と一致する。

### 誤検出と既存書庫への影響

cpio は binary 変種の magic が弱いため、検出の誤りが最大の risk である。

- コーパス 95 書庫で、cpio 検出の追加により判定が変わった書庫は無い。
  開ける書庫は 80 → **82**(`cpio-newc.cpio` と `cpio-odc.cpio` が新たに開く)。
- **救済モードを有効にしても、95 書庫すべてで strict と結果が完全に一致した**(差異 0)。
  救済の緩和が誤検出を増やしていない。
