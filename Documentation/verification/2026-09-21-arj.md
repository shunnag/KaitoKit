# ARJ の読み取り（2026-09-21）

環境: macOS 27.2 / Apple Silicon / 7-Zip 26.03 `7zz`、deark 1.7.3、The Unarchiver `unar` 1.10.8（黒箱 reader。
ARJ を書けるものは無い）。

## 裁定と進め方

候補調査（[2026-09-20-format-candidates.md](2026-09-20-format-candidates.md)）の裁定 5「開示済みの ARJ / ar002
`read_pt_len` スニペットが ARJ codec の汚染になるか」について、利用者は 2026-09-21 に「注意深く進めて、オンラインの
データもよく調査してください」と指示した。それに従い、(1) 公開資料を集めて出自を固定し、(2) ARJ 用の decoder code は
新たに書かず既存の LHA decoder を parameter 違いで呼び、(3) その同一性を実物で黒箱確認する、という進め方をとった。

## 実装と範囲

- 公開 `ArchiveFormat` に `.arj`（CLI の `detect` は `arj`、compat は `ARJ`）を追加。検出は offset 0 の header id
  `60 EA` + basic header size ≤ 2600 + header CRC-32 一致 + file type 2（main header）。MZ で始まる file は technote
  の手順（id を探し、size と CRC で確かめる）で 1 MiB まで走査する（URL open は既定、Data は `scanForSFXInData`）。
- `ARJReader`（`Sources/KaitoKit/Formats/ARJ/ARJReader.swift`）: main header → local file header の列（basic header
  size 0 が end marker）。各 header の CRC-32 を検証し、extended header（size、本文、CRC）は読み飛ばす。file type 0 / 1
  を file、3 を directory として公開し、4（volume label）/ 5（chapter label）は出さない。名前は PATHSYM_FLAG が
  無ければ `\` を `/` に置き換え（decode 後）、書庫全体で 1 つの legacy encoding を判定する（LHA と同じ規則。host が
  WIN95 / WIN32 なら Windows 側の候補）。comment、DOS 日時（technote の time stamp 図）、host OS 名、archiver
  version、`textMode`、multi-volume の flag を `formatSpecific` に出す。UNIX host の access mode を permissions に。
- method 0: stored（宣言サイズと圧縮サイズの一致を検査、CRC-32）。method 1〜3: 既存 `LZSStaticHuffmanDecoder` を
  `-lh6-`（窓 32 KiB、position 16 symbol、command 510 symbol）で呼ぶ。method 8 / 9: 本文無し（size 0）。
- 非対応（一覧はできる）: method 4（`compressed fastest`）、GARBLED_FLAG の file（`isEncrypted`、読むと
  `unsupportedMethod`。password を渡しても復号しない）、VOLUME_FLAG / EXTFILE_FLAG の続き file（multi-volume）。
- 上限: `maxEntryCount`、`maxPathComponentCount`、`maxEntrySize`、header の累積を `maxTotalMetadataSize`、
  LHA decoder の `maxDictionarySize`。
- fuzz: `Scripts/fuzz/mutate.py` に ARJ member の圧縮範囲 locator、`make-compressed-seeds.sh` に basic.arj を追加。

## 独立した検証データ

`Tests/Fixtures/arj/`（`generate.py`、`manifest.json`）。自作 ARJ writer と、LHA lh5 / lh6 の公開記述から書いた
自作 static-Huffman encoder（距離 ≤ 26,624）で作る。payload は README.TXT（26,400 byte）、DATA/TABLE.BIN（30,000
byte、窓をまたぐ）、DATA/SUB/DEEP.TXT、EMPTY.TXT、STORED.BIN（method 0）、CP932 名の `日本語.TXT`。

| fixture | 内容 | 照合 |
| --- | --- | --- |
| basic.arj | version 11、PATHSYM 名、directory 2 つ、method 1 + stored、CP932 名 | 7zz、deark、unar |
| backslash.arj | 同じ内容を DOS の `\` 区切り（PATHSYM 無し）で | 7zz、deark、unar |
| sfx.exe | MZ stub（CRC の合わない偽の header id を含む）の後ろに main header | 7zz、unar |
| nodata.arj | method 9（no data）の member を追加 | 7zz の一覧のみ（7-Zip は method 9 を展開できない） |
| garbled.arj | README.TXT を GARBLED_FLAG + 本文 xor 0x5A に | 無し（reader が拒むことだけを確かめる） |

生成中に encoder の不具合を 1 つ見つけた: 3〜18 個の zero run を表す symbol 1（4 bit）に 19 個を入れていた（4 bit の
範囲外）。7-Zip と KaitoKit が同じ member で失敗して発覚し、19 は 18 + 1 に分けて直した。7-Zip は CP932 名を生の
byte で、unar は CP1252 として書き出すので、この member は内容で照合した。extended header を持つ自作 file は 7-Zip が
受理し unar が拒む（"Data is corrupted"）。technote は「現在使われていない」としており実物も無いので fixture には
しない（reader は読み飛ばす）。

## 残る制約

- method 4（compressed fastest）は非対応。公開の bitstream 記述が見つからず、手元に encoder も実物も無い。
- garbled（暗号化）file は復号しない（technote は encryption version の番号だけを示す）。
- multi-volume（`.a01`…）の続き file は `unsupportedMethod`。各 volume は単独で開ける（先頭 volume の完結 member は読める）。
- method 2 / 3 は実物が無く、method 1 と同じ decoder で読む（wiki の記述に基づく）。
- text mode（file type 1）の member は実物が無い。technote は「original size は text mode 圧縮では異なる」と書くが、
  reader は header の original size と CRC-32 をそのまま真とする（`formatSpecific["textMode"]` を出すだけ）。
- format version 1 / 2（ARJ 0.13〜1.00、first_hdr_size が 30 未満の可能性）は実物が無く未検証。
- header の読み取りは extended header の最大量まで先読みするので、数万 member の書庫では metadata の読み込みが
  多くなる（性能上の制約。正しさには影響しない）。
- ARJ32 の long name / Unicode name（ANSIPAGE_FLAG）と、ARJZ 拡張は未検証。
