# UDF（ECMA-167 / OSTA UDF 1.02〜2.60）の読み取り追加（2026-09-21）

環境: macOS 27.2 / Apple Silicon / hdiutil・newfs_udf（OS 同梱、writer）/ macOS UDF driver（`hdiutil attach`、
黒箱 reader）/ 7-Zip 26.03（補助）。

## 実装と範囲

- 公開 `ArchiveFormat` に `.udf`（raw value `"udf"`）を追加。CD001 を持たず ECMA-167 の認識列
  （BEA01 … NSR02|NSR03 … TEA01）だけがある image を `.udf` として検出する。CD001 を伴う hybrid は
  `.iso` のまま、`ISOReader` が同じ `UDFFileSystem` で UDF の木を Rock Ridge / Joliet / PVD より優先し、
  UDF 側が `malformed` / `truncated` / `unsupported*` なら従来の木へ戻す（`limitExceeded` は戻さない）。
- volume 構造（`UDFVolume`）: anchor を sector 256 / N / N − 256 で block size 2048 / 512 / 1024 / 4096
  の候補ごとに探し、tag location が一致した候補を採用して LVD の logical block size と照合する。main VDS
  が読めなければ reserve VDS。PVD / PD / LVD は Volume Descriptor Sequence Number の最大を採用（3/8.4.3）。
  partition map は type 1、`*UDF Sparable Partition`（sparing table、packet 単位の再配置）、
  `*UDF Virtual Partition`（VAT。file type 248 の 2.x header 形式と、file type 0 で末尾に
  `*UDF Virtual Alloc Tbl` を置く 1.50 形式。VAT ICB は最終 sector、無ければ 64 sector 手前まで探す）、
  `*UDF Metadata Partition`（metadata file の extent を通した写像。main の FE が読めなければ mirror）。
- file 構造（`UDFFileSystem`）: FSD 列（Next Extent を辿り file set number 0 を採用）、ICB の direct entry
  （FE 261 / EFE 266、indirect entry 259 を辿る strategy 4096 の連結リスト、terminal 260）、short / long
  allocation descriptor と type 3 の継続 extent（AED 258）、inline data、未記録・未割当 extent の 0 埋め、
  FID（親・削除済みを除外、hidden は `formatSpecific["hidden"]`）、file type 4 / 5 / 0 / 249 / 12、その他は
  `.other` と `unsupported`。symlink は 4/14.16 の path component 列（type 1〜5）を解釈し、解釈できない本文は
  生の path として `linkTargetStoredAsData` を立てる（hdiutil の UDF 1.02 / 1.50 は生の path を書く）。
  EFE の stream directory から `*UDF Macintosh Resource Fork` を `name/..namedfork/rsrc`（`fork=resource`）
  として公開し、他の named stream は `namedStreams` に数だけ記録する。permissions は 4/14.9.5 の
  owner / group / other 3 bit を POSIX へ写し、icbtag flags の setuid / setgid / sticky を足す。timestamp は
  1/7.3（type と 12 bit の時間帯 offset、−2047 は UTC 扱い）。
- 検証: すべての descriptor tag で checksum（3/7.2.3）、CRC-16（3/7.2.6、多項式 0x1021）、Tag Location を照合する。
  上限は `maxTotalMetadataSize`（読んだ block と entry の累積）、`maxMetadataSize`（directory 本文、VAT、
  sparing table）、`maxMetadataRecordCount`（FID、AD、VAT entry）、`maxEntryCount`、`maxPathComponentCount`
  （深さ）、`maxEntrySize`。directory の循環は ICB の位置で検出し `cycleSkipped` を立てる。
- ext_ad（allocation descriptor type 2）、複数 volume の volume set、device / FIFO / socket、multisession の
  基準 sector S ≠ 0 は非対応（`unsupportedMethod` または `.other`）。

## 出自

ECMA-167 3rd edition と OSTA UDF 2.60 / 1.50 の仕様本文（`inbox/udf/`、SHA-256 は design.md §10）。仕様本文を
読む過程で UDF §6.4 の OSTA Compressed Unicode の sample C code と §6.5 の CRC 表も表示されたが、実装は
§2.1.1 の散文と 3/7.2.6 の多項式から書き、code と表は写していない。第三者 UDF 実装の source は開いて
いない。黒箱で決めた点:

- 7-Zip は hdiutil / newfs_udf の image を "Unsupported feature" で開けない。field を 1 つずつ書き換えて
  二分探索した結果、原因は **symlink（file type 12）** で、symlink を消すか file type 5 に変えると 5 file を
  一覧する。Apple の writer の逸脱ではなく 7-Zip の制限。よって主オラクルは macOS の UDF driver。
- hdiutil makehybrid（UDF 1.02 / 1.50）は symlink の本文に path component 列でなく生の path を書く。
  newfs_udf（2.01〜2.60）は仕様どおり component 列（type 5）を書く。
- newfs_udf 2.01（`hdiutil create -fs UDF`）は 512 byte block、EFE、小さい file の inline data、resource fork と
  xattr を named stream（`*UDF Macintosh Resource Fork`、xattr 名）として書く。1.02 / 1.50 の makehybrid は
  resource fork を捨てる。
- newfs_udf の `-m fix-packet`（sparable）と `-m var-packet -t wo`（VAT）は plain image 上では anchor を
  書かず mount できないため、pure150 fixture の LVD / PD / FSD を仕様どおり書き換えて sparable partition
  （sparing table で partition の packet 0 を別 packet へ再配置し、元を 0 埋め）と virtual partition
  （FSD と root ICB を virtual block 0 / 1 経由、1.50 形式と 2.x 形式の VAT ICB を最終 sector に置く）の
  合成 image を作り、macOS の driver が mount して原本と同じ SHA-256 を返すことで写像の解釈を確認した。
  最初の合成では root FE の short_ad が virtual 空間で解釈されて root directory が読めず（macOS も同じ
  結果）、VAT に他の block の identity entry を加えて解決した。

## 残る制約

- 実物の DVD-Video / Blu-ray / packet 書き込み CD-RW の image は手元に無く、writer は macOS の 2 つに
  限られる。sparable / VAT の実装確認は合成 image に対する macOS driver の挙動による。VAT ICB の位置は
  「partition 末尾の sector」の合成配置だけで確認した（閉じた session の AVDP + VAT ICB や run-out padding
  の実物は未確認。探索は partition 末尾から 512 sector 手前まで）。
- **strategy 4096（indirect entry の連鎖）は ECMA-167 4/14.7 と UDF §6.6 から実装したが独立検証が無い**:
  macOS の UDF driver は strategy 4096 の FE を持つ file を一覧から落とす（単独の DE でも同じ）ので、
  合成 image `icb-chain-4096.iso`（古い DE + IE → 新しい DE + TE）は KaitoKit が「最後の direct entry を
  採る」ことを固定するだけで、オラクルは無い。2 block の ICB に DE と terminal entry を置く strategy 4 の
  `icb-two-entries.iso` は macOS も読む。
- ISO 9660 / UDF hybrid で ISO 側だけが zisofs（Rock Ridge ZF）を持つ image は、UDF の木が生の圧縮本文
  （16 byte header 付き）を返す。そのような writer（genisoimage `-udf -z`）は手元に無く未確認で、
  UDF 優先の副作用として既知の制限に記した。
- `Scripts/fuzz/mutate.py` に UDF の payload locator は無い（ISO 全体の locator も無い）。
- hybrid で UDF 側に戻れなかった理由は公開しない（ISO 9660 の木で静かに続く）。
