# KaitoKit セキュリティレビュー

## 1. 目的と互換性条件

外部から利用される書庫展開フレームワークとして、信頼できない書庫、分割巻、暗号化書庫、破損書庫を処理した場合のメモリ安全性、ファイルシステム安全性、認証、可用性を監査した。

最優先の制約は、既存利用者との接続性を損なわないことである。当初のレビュー時点では製品ソースを変更していなかった。提案と後続の実装は、次を維持する範囲に限定する。

- `KaitoKit`、`KaitoKitCompat`、`KaitoKitDynamic` の product と公開シグネチャ
- `ArchiveReader`、`EntryStream`、`ReaderOptions`、`ReadLimits`、公開 value の意味
- `ZipRawLayout`、`SevenZipEditLayout`、`TarEditLayout`、`LHARawLayout` の SPI と、その利用者である GyoshukuKit / KaitoFinder
- 形式・復号結果・エラー順・既存のエラー種別
- macOS 26 以降、Swift 6 の concurrency 契約、OS 同梱ライブラリだけを使う構成

## 現在の実装

4 件の指摘を実装と照合し、各製品で次の対策を確認した。

| 指摘 | 実装と適用範囲 |
|---|---|
| S-01　書庫爆弾 | KaitoFinder の読取上限は 1 項目 1 TiB、書庫合計 4 TiB。実際の入力長の 1,024 倍と 1 GiB の大きい方でも総量を制限する。圧縮コンテナの一時展開と未申告サイズにも適用する。編集用に元の書庫を開き直す場合も、GyoshukuKit に絶対上限と展開倍率を渡す。 |
| S-02　cpio・tar | 生の名前・リンクなどの保持コストを公開 entry の構築段階まで引き継ぐ。合計予算のちょうど境界を回帰試験で確認する。 |
| S-03　並列復号 | KaitoFinder の展開処理は物理メモリの半分を並列用に共有し、独立 reader に worker 数で割った予算を渡す。直列復号や metadata はこの予算の対象外。 |
| S-04　出力先 | KaitoFinder は選択した通常ファイルと本体付き hard link の既知サイズをボリューム別に合計し、既存の出力名を除いて開始前に照合する。個々の出力先でも単一ファイル上限を照合し、実書き込み前に空き容量と他 worker の書き込み中のバイトを確認する。各ボリュームで初回空きの 5% と 1 GiB の小さい方を残す。 |

64 MiB の読み取り専用 FAT32 ボリュームで、単一ファイル上限として 4,294,967,295 byte（4 GiB − 1 byte）を取得した。ほかのボリュームでは macOS が報告する上限を使い、値を取得できない場合も書き込み時の OS エラーを伝える。空き容量は他プロセスとも共有するため、事前確認後の書き込み失敗にも対応する。圧縮 tar / cpio は一覧を開く際に外側のストリームを一時展開するので、各メンバーの合計とは別に、この中間ファイルも 1 TiB と倍率の上限に収まる必要がある。

## 追加確認（2026-11-27）

- **tar のメタデータ**。解析中の配列は公開一覧の構築中も残る。両方の論理コストを `maxTotalMetadataSize` に合算した。名前が 1 バイトの通常ファイル 2 件を使い、arm64 では 1,132 バイトで受理、1,131 バイトで拒否することを、通常読みと復旧読みで確認した。
- **本体付きハードリンク**。KaitoKit は既に展開した参照先を同じ inode のまま更新する。更新前に元データを退避し、書き込み・検証・新しいリンク名の公開に失敗したら元データを復元する。容量不足を最初の書き込み後に発生させ、参照先と先行リンクの内容・inode・権限・更新日時、上書き予定の別ファイルの内容が保たれることを確認した。クローン非対応時のコピーと末尾の復元も試験した。KaitoFinder の本体付きリンクは元から独立した通常ファイルとして展開する。
- **パスワード**。KaitoFinder は対象書庫の保存値を 1 件だけ自動で試し、誤りならその保存値を削除して入力を求める。別の候補を自動で繰り返す経路は確認されなかった。個別 KDF の上限と並列照合の worker 制限は引き続き適用する。
- **編集と大容量**。KaitoFinder の展開倍率を、GyoshukuKit が編集用に完全な書庫を開くときにも引き継ぐ。ZIP・7z・LHA・tar の updater と再構築の計 5 経路で、許容量ちょうどを受理し、1 バイト超過を拒否した。追加部分だけを切り出した ZIP / LHA の自己検査では絶対上限を使う。通常の Finder 設定で、ZIP64 の 4,294,967,297 バイトを終端までストリームで読み、CRC-32 `41d912ff` を確認した。68 GiB の tar は全 17 項目を一覧し、各 4 GiB、合計 73,014,444,032 バイトを 1 MiB のバッファで終端まで読み切った。いずれも入力は sparse ファイルで、このストリーム試験は展開先に本文を書き込まない。
- **制限を解除する設定**。KaitoFinder では、閲覧と編集の双方で有限の設定を既定とし、すべての出力制限を解除する UI は追加しなかった。埋め込みアプリは読取時の絶対上限と展開倍率を別々に指定できる。

最終の KaitoKit と Compat の全テストは計 2,164 件の結果で失敗 0。Release の Thread Sanitizer は関連 109 件中 108 件成功、外部の大容量 XZ を使う任意試験 1 件がスキップ、診断 0 だった。Address Sanitizer は展開・容量境界の 49 件と、PPMd 最適化候補の 11 件が成功した。最終の framework は arm64 と x86_64 の両方を含む。
