# WIM（Windows Imaging）の読み取り追加（2026-09-21）

環境: macOS 27.2 / Apple Silicon / 7-Zip 26.03（黒箱 reader、stored の writer）/ 利用者所有の Microsoft 製
`boot.wim`（Surface Pro 4 回復 image、848,679,996 byte、LZX、chunk 32 KiB、1 image、29,335 entry。
リポジトリには入れない）。

## 実装と範囲

- 公開 `ArchiveFormat` に `.wim`（raw value `"wim"`、署名 `MSWIM\0\0\0`）を追加。header（version、flags、
  chunk size、part / total、image 数、lookup table / XML / integrity の RESHDR）、lookup table（50 byte entry:
  RESHDR_DISK_SHORT + part + 参照数 + SHA-1）、image ごとの metadata resource（SECURITYBLOCK_DISK を飛ばし、
  8 byte 境界の root DIRENTRY から `subdirOffset` で木を辿る）を読む。
- resource: 無圧縮、または chunk 表（元サイズが 4 GiB 超なら 8 byte、それ以外 4 byte の次 chunk 位置）と
  chunk 列。chunk の格納長が展開後長と同じなら無圧縮 chunk。XPRESS は新規の `XpressHuffmanDecoder`
  （[MS-XCA] §2.2）、LZX は既存 `LZXDecoder` に WIM 変種を追加。読み取り時に lookup table の SHA-1 と照合し、
  不一致は `checksumMismatch`。
- entry: file / directory、alternate data stream（`name:stream`、`formatSpecific["stream"]`）、hard link 群
  （`hardLinkGroup`）、reparse point のうち symbolic link（`0xA000000C`）と junction（`0xA0000003`）は
  resource の REPARSE_DATA_BUFFER から `linkPath`（`\??\` を外し `\` → `/`、`linkTargetAbsolute`）を取る
  `.symlink`、他の tag は `.other`。EFS 暗号化（attribute 0x4000）は `unsupportedMethod`。`attributes`、
  `image`、`sha1`、`hidden` を `formatSpecific` に出す。日時は LastWriteTime（FILETIME）。
- image が 2 つ以上なら `1/`、`2/` を前置する（7-Zip と同じ）。`.swm` は part 1 だけ開き、他 part の resource は
  `unsupportedMethod("WIM resource in part N")`。version 0.14 / LZMS flag（solid、ESD）は `unsupportedMethod`。
- 上限: lookup table は `maxMetadataSize`、metadata resource は `maxTotalMetadataSize`（install.wim の metadata は
  数十 MB）、directory 数・entry 数・深さ・path component、chunk 表は `maxMetadataSize`。

## 出自

Microsoft の公開 whitepaper "Windows Imaging File Format (WIM)"（2007）と [MS-XCA]（LZ77+Huffman の散文と
擬似コード）、[MS-FSCC]（reparse data buffer）、既存の [MS-PATCH] 由来 LZX decoder。第三者 WIM / LZX / XPRESS
実装の source は開いていない。whitepaper に無い点を黒箱で決めた:

- **DIRENTRY の固定部は 102 byte**（whitepaper の struct より 4 byte 長い。7-Zip 製 WIM の dump で
  `wStreams` @96、`wShortNameLength` @98、`wFileNameLength` @100、名前 @102）。root DIRENTRY の後にも
  8 byte の終端が置かれ、子は `subdirOffset` から始まる。
- header の lookup table / XML の RESHDR は 7-Zip 製・Microsoft 製とも METADATA flag（0x02）を持つ。
  無くても 7-Zip は開く（flag 0 の合成 WIM で確認）ので、fixture の writer は慣例に合わせて立てるだけ。
- root DIRENTRY の直後にも 8 byte の終端が置かれる（無いと 7-Zip は開けない）。
- **LZX の WIM 変種**: (1) stream 先頭の E8 header bit が無く、変換サイズは常に 12,000,000（変換無しでは
  boot.wim の 40 resource 中 9 が SHA-1 不一致、12,000,000 で全一致）、(2) block header は 3 bit の type の後に
  1 bit（1 = block size 32768、0 = 16 bit の size が続く。末尾 chunk の header を dump して確認）、
  (3) 奇数長の生 block が chunk 末尾に来ても pad byte が無い（manage-bde.exe ほか 22 resource が
  `truncated` になっていた原因）、(4) 各 chunk は独立した stream で E8 の位置は chunk 先頭基準、
  (5) 窓は 32 KiB（chunk size）。これらで boot.wim の全 23,491 file + 310 ADS（3.36 GB）の SHA-1 が一致した。
  生 block 直前の padding（整列済みでも 1 word を消費する [MS-PATCH] 2.3.2.1 の規則）は boot.wim の 165 個の
  生 block がすべて非整列で始まるため WIM で確認できておらず、CAB と同じ規則を適用している。
- XPRESS の symbol 256 は「長さ 3・距離 1 の match」と終端の両方を表す（[MS-XCA] §2.1.4.1 の式と §2.2.4）。
  出力が揃うまでは match として扱う。7-Zip も同じ（自作 encoder の出力を展開）。
- reparse point の resource は REPARSE_DATA_BUFFER の header（tag、length、reserved）を含む（header 無しの
  本体だけを置いた合成 WIM は 7-Zip が "Incorrect reparse stream" で拒み、header 付きは `link -> a.txt` を作る）。
- 7-Zip の WIM writer は stored だけ（`-mm=LZX` 等は E_INVALIDARG）。

## 独立した検証データ

`Tests/Fixtures/wim/`（`generate.py`、`manifest.json`、`README.md`）: 自作 WIM writer による stored（ADS、
hard link 群、空 file、symlink reparse point、日本語名）、XPRESS、LZX、LZX + chunk 末尾の奇数長生 block、
2 image、および 7-Zip 26.03 が書いた stored の 6 本（2.7〜51 KB）。XPRESS / LZX の encoder は [MS-XCA] /
[MS-PATCH] の散文から書き、**全 fixture は生成時に 7-Zip が展開して原本と一致**することを確認してから保存
した（自作 encoder の妥当性は 7-Zip が、decoder の妥当性は fixture と boot.wim が示す）。

## 通過した検証

- `WIMReaderTests` 5 件、失敗 0: stored 2 本（自作・7-Zip）の全 file の SHA-256、ADS、symlink、hard link 群、
  日時 / attributes、`reopen()`; XPRESS / LZX / LZX-raw の全 file（一括、chunk 1,000、chunk 1）と生格納 chunk、
  圧縮 chunk 破損の拒否; 2 image の `1/` `2/` 前置と共有 resource; version 0.14、part 2、lookup table 長、
  切り詰め、上限 3 種、SHA-1 書き換えの `checksumMismatch`; XPRESS / LZX decoder のゴミ入力。
- 開発時（リポジトリ外）: Microsoft 製 boot.wim の一覧が 7-Zip と一致（29,025 path + 7-Zip が既定で隠す 310 ADS）、
  `kaito sha` が 29,335 entry すべてで lookup table の SHA-1 と一致（58 秒）、無作為 30 file の SHA-256 が
  7-Zip の展開結果と一致。
- `CabLZXTests` ほか既存 CAB suite（LZX decoder の変更が CAB に影響しないこと）。

## 残る制約

- solid / ESD（LZMS）、分割 `.swm` の他 part、EFS 暗号化 file、symlink / junction 以外の reparse point、
  security descriptor、integrity table の検証、XML の image 名は未対応。
- 実物の XPRESS WIM と reparse point 付きの Microsoft 製 WIM は手元に無く、自作 encoder + 7-Zip 展開による
  検証に留まる。chunk 途中（末尾でない）の奇数長生 block の pad byte と、整列済みで始まる生 block の padding は
  CAB の規則を仮定し、標本が無い。
- chunk size は 32 KiB だけ対応（LZX の窓と XPRESS の 1 block = 1 chunk の前提）。他の chunk size は
  `unsupportedMethod("WIM chunk size N")`。
- install.wim（10 前後の image、各 10 万 file）の規模は未検証。metadata buffer は image ごとに
  `maxTotalMetadataSize` 以内で確保して捨てるが、全 image の entry を一度に公開するので entry 数は
  `maxEntryCount`（既定 100 万）と memory に依存する。image を選んで開く option は未実装（製品判断）。
- reparse point の target は open 時に resource（1 chunk）を展開して読む。WinSxS の symlink が数千ある image では
  open が遅くなる可能性がある（未計測）。
- `Scripts/fuzz/mutate.py` に WIM の payload locator は無い。
