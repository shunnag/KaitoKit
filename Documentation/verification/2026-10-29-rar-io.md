# RAR header and split-volume IO (2026-10-29)

Items: n7jl.5 and n7jl.6. Baseline: `f17f31fbdbf0e1697d9b71af9f4961318aa76556`
(`HEAD` when this work started), branch `perf/rar4-io`.

## Implementation

RAR4 high-latency listing reuses `HeaderReadPlanner` / `HeaderWindowByteSource`.
Its median-spacing cutoff is now 256 KiB, with the existing 256 KiB–1 MiB
adaptive windows. The default cutoff for other callers remains 64 KiB. RAR4
`.low` still uses fixed 16 KiB windows, and sparse runs still use 16 KiB hops.
The larger cutoff trades payload transfer for fewer sequential round trips:
256 KiB is below the existing planner's approximate 9 ms / 30 MB/s break-even
point. There is no RAR4 index from which to discover all future header offsets
without reading their predecessors.

RAR4 and RAR5 now retain bytes during their existing packed-part integrity
pass and decode from those verified bytes. The shared `RARVerifiedPackedParts`
retains at most `min(inMemorySingleFileLimit, 4 MiB)` of packed data in memory for
one logical file, plus the materializer's bounded scratch/write buffer (up to
4 MiB), using `SingleFileMaterializer`'s already-unlinked temporary
file for larger data. This cap applies across all parts, rather than per part.
Only ranges with an enabled packed CRC/hash are staged. The unchecked final
part stays on its original source, so its reads and failures still occur at
decode time. Encryption still sees one concatenated CBC stream, including
cross-volume chaining; RAR5 checksum MACs and optional BLAKE2sp remain enabled
under the same conditions as before.

The pre-decode pass cannot be deferred while preserving the existing contract:
a corrupt checked part must fail when requesting a stream, before any decoded
output is available. RAR4 still checks packed CRCs before requesting/deriving
the data password. RAR5 still performs its password-check/KDF step before the
packed checks, and a password-dependent packed mismatch without an independent
password verifier still reports `wrongPassword` at stream creation. Retaining
the verified bytes removes the second read from the archive volumes without
moving these errors into extraction.

If local staging fails (including its free-space reserve), the scanner finishes
the historical integrity pass without caching and returns the original ranges.
This exceptional mode retains the original two source reads. It avoids adding
a new storage error or masking the archive's checksum/password error. Archive
read failures and cancellation propagate; they are not retried as cache failures.
Disk staging itself necessarily writes and later reads the local temporary file;
the eliminated IO is the second read from the original volume set.

## Fixtures and commands

`RARIOTests` generates four 64-entry RAR4 archives: 96 KiB and 192 KiB
deterministic incompressible files, each solid and non-solid. It also generates
256 KiB volume sets from a 2,097,289-byte deterministic payload, covering stored,
compressed, solid, encrypted stored/compressed, and header-encrypted files for
both versions. RAR5 additionally covers BLAKE2sp and encrypted BLAKE2sp with the
optional password-check field removed using KaitoKit's existing test helper.
Solid sets include a second member. Input bytes are compared directly on decode.

The generator's command shapes (run below its `input` directory) are:

```sh
rar6=/Users/nagash/.local/opt/rar-6.24/rar
"$rar6" a -ma4 -idq -m3 -s  -ep1 headers-96-true.rar 'small-96/*'

"$rar6" a -ma4 -idq -s- -v256k -m0 chain.rar split.bin
"$rar6" a -ma5 -idq -s- -v256k -m3 -psecret chain.rar split.bin
```

## Measurements and validation

These are source-call/returned-byte counts, not physical NAS wall-clock claims.
`CallCountingByteSource` measures listing with explicit low/high and automatic
policy on a source reporting a nonlocal volume. `FileByteSource.testingDidRead`
registers all original volume handles during opening, then counts their reads
after resetting at extraction. Local staged-file reads are excluded. Both forced
disk (`inMemorySingleFileLimit = 0`) and memory (4 MiB) staging gave the same
original-volume counts.

### Full-suite CLI capture workaround

Two initial full-suite attempts were interrupted after stalling in the existing
`CLISmokeTests.testBenchRandomReadsTwentyEntriesFromSolidSevenZip`. The test
runner's `KaitoCLI.run` waits for child termination before draining pipes. The
same commands succeed directly; using file capture and forwarding output after
the launcher exits makes the isolated test pass (1 test, 0 failures, 0.552 s).
The CLI workaround changes no repository harness file. It uses the existing
`KAITO_EXECUTABLE` override with this temporary launcher, preserving argument
passing, stdin, output bytes, and exit status:

```sh
#!/bin/sh
if [ ! -p /dev/fd/1 ] && [ ! -p /dev/fd/2 ]; then
  exec /Users/nagash/Github/KaitoKit-wt-rario/.build/out/Products/Debug/kaito "$@"
fi
capture_dir=$(mktemp -d /tmp/kaito-rar-cli.XXXXXX) || exit 1
chmod 700 "$capture_dir" || exit 1
/Users/nagash/Github/KaitoKit-wt-rario/.build/out/Products/Debug/kaito "$@" \
  > "$capture_dir/out" 2> "$capture_dir/err"
result=$?
chmod 600 "$capture_dir/out" "$capture_dir/err"
(cat "$capture_dir/out"; rm "$capture_dir/out"; \
  rmdir "$capture_dir" 2>/dev/null || true) 2>/dev/null &
(cat "$capture_dir/err"; rm "$capture_dir/err"; \
  rmdir "$capture_dir" 2>/dev/null || true) >&2 &
exit "$result"
```

release command above, make `/tmp/kaito-rar-io-cli-capture-release` with the same
