# pbzx（Apple flat package の Payload / OTA の chunked XZ）の読み取り追加（2026-09-20）

環境: macOS 27.2 / Apple Silicon / `pkgbuild`・`xar`（OS 同梱）/ xz 5.8.4 / libarchive 3.7.4（`bsdtar`）。

## 形式（黒箱計測）

Apple は pbzx の文書を公開していない。本実装は macOS 27.2 の `pkgbuild --compression latest`
（`--min-os-version 10.10`）が書いた flat package から `xar -xf` で取り出した Payload を、
`xz` CLI と `bsdtar` だけで解析して確定した layout に従う。第三者の pbzx 実装・記事は参照していない。

| offset | size | 内容 |
|---|---|---|
| 0 | 4 | `pbzx` |
| 4 | 8 | BE64: chunk の展開後サイズの上限（pkgbuild は 0x01000000 = 16 MiB） |
| 12 | — | chunk の列。各 chunk は BE64 展開後サイズ U、BE64 格納長 L、L byte の本文 |

本文が XZ 署名（`FD 37 7A 58 5A 00`）で始まれば XZ stream（展開後 U byte）、そうでなければ
L == U の生 byte。最後の chunk の U は上限より小さくてよく、chunk 間や末尾の padding は無い。
40 MB の入力では 16 MiB / 16 MiB / 7,767,040 の 3 chunk になり、各 chunk を `xz -d` した連結が
odc cpio（`070707`）になって `bsdtar` で原本と一致した（20 MB 乱数 file の SHA-256 一致）。
生の chunk は pkgbuild の出力には現れなかったので、自作の包み直し（fixture）で検証した。

## 実装と範囲

- 公開 `ArchiveFormat` に `.pbzx` を追加し、署名 `pbzx` で検出する。
- `PbzxDecompressor` は header の chunk size（0 は `malformed`、`maxDictionarySize` と 16 MiB の
  大きい方までを受理）を読み、chunk header ごとに U ≤ chunk size と L が file 内に収まることを検査、
  XZ chunk は既存 `XZDecompressor`、生 chunk は `CopyDecompressor` で返し、出力長が U に一致しない
  chunk は `malformed`。chunk 数は `maxMetadataRecordCount`、U の合計は `maxEntrySize` で制限し、
  open 時に合計（`contentSize`）を確定して entry の `uncompressedSize` にする。
- `ArchiveReader` は pbzx を圧縮 tar / cpio と同じ staging 経路に流し、展開結果の先頭が cpio magic
  なら `CpioReader` で entry を直接公開する（format は `.cpio`）。そうでなければ単一 stream
  （method `XZ (pbzx)`）。`reopen()` は保持済みの展開結果から開き直す。
- あわせて圧縮 cpio の名前による連鎖（`.cpgz`、`.cpio.gz|bz2|xz|zst|lz4|lzma|lz|br|Z`）と、
  PE / Mach-O prefix の後ろの CAB（`MSCF` + reserved 0 + version 1.3 を SFX 走査に追加）を実装した。
  `compressedTarFormats(for:)` は container と codec 集合を返す `compressedContainer(for:detected:)`
  になった。

## 独立した検証データ

`Tests/Fixtures/pbzx/`（`generate.py`、`manifest.json`、`README.md`）: pkgbuild 製 Payload
（xz chunk 1 個、22,528 byte の odc cpio）、同じ cpio を「生 chunk + xz chunk」に包み直したもの、
cpio でない text を 2 つの xz chunk に包んだもの。生成器は各 chunk を `xz -d` で復号し、cpio は
`bsdtar -tf` / `-xOf` で全 entry を原本と照合してから保存する。

## 通過した検証

- `PbzxTests` 3 件、失敗 0: 3 fixture の chunk ごとの復号と `contentSize`、pkg Payload の cpio としての
  一覧（4 file の SHA-256、`reopen()`）、cpio でない stream の単一 entry 公開（Data / URL、名前
  `Payload`）、magic / chunk size 0 / 上限超過 / 格納長超過 / 切り詰め 6 箇所 / 展開後サイズ不一致 /
  生 chunk の長さ不一致 / 空 chunk / header のみ、entry 上限と chunk 数上限。
- `CompressedCpioAliasTests` 2 件: `.cpgz` / `.cpio.gz` / `.cpio.xz` / `.cpio.lz` / `.cpio.bz2` /
  `.cpio.zst` の cpio 列挙、元 file 削除後の `reopen()`、名前の無い Data は単一 stream、cpio でない
  `.cpgz` の拒否、合計上限、memory / disk staging。
- `CabSFXTests` 2 件: stored / MSZIP / multiblock cabinet を 68 byte〜40,000 byte の PE prefix の後ろに
  置いた `.exe` の検出・一覧・`reopen()`、Data では `scanForSFXInData` が必要、prefix 内の偽 `MSCF`
  の読み飛ばし、1 MiB の走査上限、署名直後で切れた cabinet。
- release CLI: pkgbuild 製 test.pkg（gzip Payload、旧形式）と latest.pkg（pbzx Payload）を xar として
  一覧し、Payload を取り出して開くと pbzx 側は cpio の 3 file を直接列挙した。

## 残る制約

- xar（`.pkg`）を開いたときの Payload は従来どおり xar の 1 entry で、pkg → Payload → cpio の
  自動降下は行わない（`.deb` の入れ子 tar と同じ判断）。Payload を取り出して `ArchiveReader.open`
  すれば pbzx / gzip の連鎖が働く。
- 生 chunk と 16 MiB 以外の chunk size は pkgbuild の出力に現れず、自作 fixture でだけ確認した。
