# lzip（`.lz` / `.tar.lz`）の読み取り追加（2026-09-20）

環境: macOS 27.2 / Apple Silicon / XZ Utils 5.8.4（`xz -d --format=lzip`）/ libarchive 3.7.4
（`bsdtar --lzip`、OS 同梱）/ Python 3.14 `lzma`（raw LZMA1 encoder）。

## 実装と範囲

- 公開 `ArchiveFormat` に `.lzip`（raw value `"lzip"`）を追加。単一 stream `.lz` と、名前が
  `.tar.lz` の圧縮 tar を読む。`.tlz` は GNU tar が LZMA_Alone、lzip 自身が tar.lz に使うので、
  署名で判別した方を tar 経路に流す（`compressedTarFormats(for:)` が集合を返すようにした）。
- member: `LZIP` + version 1 + 辞書サイズ 1 byte（2^e − n/16、4 KiB〜512 MiB）+ LZMA-302eos
  stream（lc=3 / lp=0 / pb=2、end marker）+ trailer（CRC-32、data size、member size）。
  open 時に末尾の member size を後ろへ辿って索引（`LzipMemberIndex`）を作り、各 member の magic・
  version・辞書・data size を検証して展開後サイズを確定する。索引の件数は `maxMetadataRecordCount`、
  辞書は `maxDictionarySize`、合計サイズは `maxEntrySize` / `maxTotalUncompressedSize` で制限する。
- 復号（`LzipDecompressor`）は member ごとに既存 `LZMADecoder` を end marker 終端で走らせ、
  出力長が data size に一致すること、range decoder が member の stream 範囲を byte 単位で使い切った
  こと（`consumedEntireInput`）、CRC-32 が trailer と一致することを検証する。
  `LZMADecoder` に `consumedInputOffset` / `consumedEntireInput` と、辞書確保量を抑えるための
  `outputSizeHint`（終端判定には使わない）を追加した。
- 末尾の余分な byte、先頭の余分な byte、切り詰め、multimember 中の空 member は `malformed` /
  `truncated`。先頭 member の version が 1 でない file（version 0 / 2）は、後ろから辿る前に
  `unsupportedMethod("lzip version N")` にする（検出は `LZIP` magic だけを見る）。
- `Scripts/fuzz/mutate.py` に member size を辿る lzip の payload locator を追加した。
- `ArchiveFormat` の網羅的 switch を持つ利用側には、新しい case の追加が必要。

実装入力は draft-diaz-lzip-14 §2 "File Format"（散文のみ。`inbox/lzip/draft-diaz-lzip-14-prose.txt`、
SHA-256 `52e63dc6e3e4ded7f1c389d1ba341ea0d47bd28c5602c10eda37e48566f6f6bf`。§3.1–3.5（lzd 参照
実装に沿った復号手順）と付録 A（参照ソース）は写しに含めず、開いていない）と既存 KaitoKit の
LZMA1 decoder である。CRC-32 の多項式は仕様の散文に無く、fixture の trailer が RFC 1952 の CRC-32
（zlib `crc32`）と一致することを黒箱で確認した。「消費 byte 数 = member size − 26」の規則も
仕様には明記が無く、libarchive / Python liblzma が書いた全 member でこの検査が通ることで確認した。
lzip / plzip / lzlib / libarchive / XZ Utils の source は開いていない。

## 独立した検証データ

`Tests/Fixtures/lzip/`（`generate.py`、`manifest.json`）: project-owned の text / 構造化 binary /
乱数 8 KiB / 空 / 1 byte を Python `lzma` の raw LZMA1（lc=3 / lp=0 / pb=2）で圧縮し、§2 の
header / trailer を生成器で付けた 7 本（辞書 4 KiB、64 KiB、320 KiB（§2 の例 0xD3）、1 MiB、
3 member の multimember を含む）と、`bsdtar --lzip` が書いた `bundle.tar.lz`。**すべて XZ Utils の
`xz -d --format=lzip` で復号して原本と一致することを確認してから保存**した。archive と展開結果の
SHA-256 は manifest に記録。

## 通過した検証

- `LzipTests` 9 件、失敗 0: 全 fixture の byte 一致（入力 chunk 1 / 7 / 4 KiB / 64 KiB）と索引の
  整合、multimember と単体連結の同値、分数辞書、DS byte の符号化（仕様の例 0xD3 = 320 KiB、
  無効値 6 種）、構造破壊 13 種の型付き拒否、stream 本体の byte 破壊（97 byte おき）で
  未検証出力が出ないこと、上限（entry / 合計 / member 数 / 辞書）、Data / URL open、名前の
  fallback（`.lz` 除去、`.tlz` → 圧縮 tar 扱い）、`reopen()`、`.tar.lz` / `.tlz` の tar 経路。
- 既存 `CompressedTarAliasTests`（`.tlz` = LZMA_Alone の固定）、`SingleFileFormatTests`、
  `SingleFileArchiveReaderIntegrationTests`、`CLISmokeTests`、Compat 全件が通過。
- release CLI: `bsdtar --lzip` の 200 KB tar（単体 `.lz` として 201,728 byte、2 連結 403,456 byte、
  `.tar.lz` として tar entry）が `xz -d --format=lzip` の出力と SHA-256 一致。

## 残る制約

- lzip 本家 / plzip の実書庫は手元に writer が無く、libarchive と Python liblzma の出力および
  自作 framing だけで検証した。両者は独立した LZMA1 encoder ではない（どちらも liblzma）。
- 「消費 byte 数」の検査は encoder が range coder を 5 byte で flush する慣習に依存する。異なる
  flush 長で書かれた member は `malformed` になる（black-box 外）。
- 索引は末尾から辿るため、切り詰められた file は救済しない（`recoverDamagedArchives` の対象外）。
